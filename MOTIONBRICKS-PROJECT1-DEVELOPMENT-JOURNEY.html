1. Establish the real starting point

01 / inventory

Find the requested workspace

The working directory was a dedicated Windows folder containing private video notes and a transcript, but no Git repository. I kept those source files locally and cloned the code into a new motion-bricks.cpp/ subfolder.

The transcript explains the video’s intent: local, low-VRAM or CPU inference, a demonstrated Unreal bridge, and problems with dropped frames, repeated short walks, and delayed response. I treated those as observations from the video, not as promises about this laptop. The repository itself was the authority for supported code paths.

02 / machine

Measure the available machine

Windows reported an Intel Core i5-12450H (8 cores, 12 logical processors), 32 GB RAM, an NVIDIA RTX 3050 Laptop GPU with 4 GB VRAM, and Windows 11 Home. Unreal Engine 5.8, Visual Studio 2022 Build Tools, CMake, Git, Go, Python and Ninja were present. Ubuntu 24.04 was already installed under WSL. A Vulkan runtime was present, but this project did not build or benchmark the Vulkan backend.

Decision: first make the repository’s own browser demo work on CPU. That proves model loading, planning, control, streaming and display before an Unreal bridge adds another source of latency or retargeting error.

2. Read and acquire the code

03 / scope

Separate MotionBricks from the video’s broader stack

The repository is a C++23/GGML port of NVIDIA MotionBricks. Its released G1 path predicts root motion and 34-joint local rotations from recent pose context and targets. It has a stable C interface, CPU and optional Vulkan inference, a Go binding, and a Three.js demo. SONIC/MuJoCo physics and Kimodo-authored clips are optional additions. The demo intentionally shows a skeleton, not a textured or skinned avatar.

The video also discussed future object interactions and separate tools for rigging or text-to-animation. Those do not become features of this Project 1 merely by installing this repository. See the repository README, API guide and demo guide.

04 / checkout

Clone the pinned GGML dependency too

git clone --recurse-submodules https://github.com/localai-org/motion-bricks.cpp.git motion-bricks.cpp

At build time the checkout was commit 2727a456e0a99baf64476496cd58115fef717944; its ggml/ submodule was 8c63e70982c95ceb862e3a1073a2c1beef75d60a. --recurse-submodules matters: without the pinned GGML source, the build can fall back to an ABI scaffold rather than the neural inference path. The upstream source checkout remained unmodified.

05 / assets

Download and verify the released model

cd motion-bricks.cpp
python scripts/download_gguf_weights.py

The repository’s downloader fetched the pinned LocalAI-io/MotionBricks-G1-GGML distribution into generated/g1-f32/ and generated/styles/. It verified every file against the version-controlled SHA-256 manifest. The bundle contains 21 files totaling 733,427,543 bytes: four GGUF components plus manifests and 15 .mbstyle files. The “all bundles present and verified” message was the acceptance gate; a download completing alone would not establish integrity.

3. The native Windows fork, and why it ended

06 / attempt

Try the existing Visual Studio compiler

cmake -S . -B build/windows-cpu -G "Visual Studio 17 2022" -A x64 \
  -DMOTIONBRICKS_ENABLE_VULKAN=OFF \
  -DMOTIONBRICKS_DOWNLOAD_MODELS=OFF \
  -DMOTIONBRICKS_BUILD_TESTS=ON
cmake --build build/windows-cpu --config Release --parallel 4

Configuration succeeded under MSVC 19.44 and found the GGML CPU variants. Compilation produced a Windows motionbricks.dll. The overall build then failed while linking the CLI and test executables, reporting many unresolved imported GGML symbols, including __imp_ggml_free. This proves a final-link boundary; it does not, by itself, prove the underlying cause of the linkage mismatch.

07 / decisive check

The supplied browser binding excludes Windows

A Windows go build failed with build constraints exclude all Go files ... bindings/go. The binding source starts with //go:build linux || darwin || freebsd. Even a repaired Windows C++ link would therefore not launch the supplied Go demo without additional porting. That concrete source boundary made WSL the shortest supported route to Project 1. See the binding.

4. Build the supported CPU path inside WSL

08 / preflight

Use Ubuntu without disturbing its CUDA packages

Ubuntu already had GCC/G++ 13 and make, but no Linux CMake or Go. An apt-get update succeeded; apt-get install cmake ninja-build golang-go failed because that Ubuntu installation had pre-existing unmet CUDA and other dependencies. I did not run apt --fix-broken install or remove CUDA packages. Portable official CMake 3.31.5 and Go 1.26.3 Linux archives were downloaded and extracted into this project’s .tools/ directory. They are local build tools, not a system-wide installation.

09 / native library

Configure one CPU backend and compile

The actual WSL build used a separate build/wsl-cpu/ directory and Unix Makefiles. The meaningful settings were Release optimization, Vulkan off, model re-download off, and GGML’s “all CPU variants” off. CMake selected an AVX2-capable CPU backend for this build. The commands below show the same relative operations from the repository directory inside Ubuntu:

../.tools/cmake-3.31.5-linux-x86_64/bin/cmake -S . -B build/wsl-cpu \
  -G "Unix Makefiles" -DCMAKE_BUILD_TYPE=Release \
  -DMOTIONBRICKS_ENABLE_VULKAN=OFF \
  -DMOTIONBRICKS_DOWNLOAD_MODELS=OFF \
  -DMOTIONBRICKS_CPU_ALL_VARIANTS=OFF \
  -DMOTIONBRICKS_BUILD_TESTS=ON
../.tools/cmake-3.31.5-linux-x86_64/bin/cmake --build build/wsl-cpu \
  --target motionbricks_shared motionbricks-cli --parallel 4

libmotionbricks.so and bin/motionbricks-cli linked successfully. An optional Python reference fixture check printed that safetensors was absent; it did not prevent this runtime build. The CLI later reported ABI version 1 and inspected the accepted G1 bundle as 183,148,382 parameters with 34 joints.

10 / browser server

Build the Go half independently

cd demo
CGO_ENABLED=0 ../../.tools/go/bin/go build \
  -o ../build/wsl-cpu/bin/motionbricks-demo .

The Go executable uses the repository’s PureGo binding to load the compiled C++ shared library at runtime. CGO_ENABLED=0 is appropriate for this Go build; it does not mean the C++ inference library was skipped. The Go executable compiled successfully before the native library build had finished.

5. Turn the build into a usable local application

11 / start

Run the model, styles and server together

run-demo.sh changes into the checkout and starts the executable with the shared library, model directory, styles directory and explicit CPU device. Its essential invocation is:

./build/wsl-cpu/bin/motionbricks-demo \
  -listen 127.0.0.1:8080 \
  -library ./build/wsl-cpu/libmotionbricks.so \
  -model ./generated/g1-f32 \
  -styles ./generated/styles \
  -device cpu

The address 127.0.0.1 limits the server to this laptop. The Windows browser reaches the WSL service through localhost forwarding. The first real startup printed MotionBricks demo: http://127.0.0.1:8080.

12 / make it repeatable

Build novice-friendly Windows launchers

Start-MotionBricks.cmd calls Start-MotionBricks.ps1, which starts the WSL server hidden, waits for its health endpoint, and opens the browser. Stop-MotionBricks.cmd calls a matching stop script that checks the recorded Linux process before terminating it. Logs and process IDs live in .state/. This leaves the source checkout untouched and avoids asking a beginner to type Linux commands each time.

Launcher fixes: the first attempt passed a Windows path to wslpath in a way that stripped its backslashes; the script now converts the known drive path to /mnt/c/.... A later version redirected the WSL process’s streams from Windows and made the wrapper wait for the server to exit. Logging was moved into the Bash launcher, after which the Windows command returned normally. Both double-click entry points were tested.

6. Prove more than “the page opens”

Gate A / files

Accepted assets

The downloader verified all 21 distribution files. The source checkout stayed clean; model data and build output occupy generated/build folders.

Gate B / native

Accepted model

motionbricks-cli abi returned ABI 1. inspect generated/g1-f32 recognized g1skel34, 183,148,382 parameters and 34 parent-linked joints.

Gate C / live

Real generation

/api/health returned {"ok":true}. /api/meta returned 15 styles and 34 joints. The Chrome viewer displayed the skeleton and target ghost; W produced forward motion.

A wrong endpoint taught us who owns motion

An early HTTP POST /api/session returned HTTP 410: “motion commands are owned by the WebSocket session.” This was not a broken model. The current demo intentionally sends controls through the WebSocket at /api/stream/socket; HTTP still supplies health, metadata and upload functions. The live browser and a separate WebSocket probe established actual inference.

Measure response without conflating clocks

A controlled eight-second WebSocket run on port 8081 requested walking and received 168 pose messages spanning 162 server ticks, with 2.81 m root displacement. Its requested planner call took 461 ms; the acknowledgement arrived after about 4.6 s in that first measurement. The test did not isolate why the acknowledgement took longer than the planner call. The effective tick advance was about 20 per wall-clock second in that sample, below the nominal 50. Later warm plans in the server log included values around 260–440 ms. Those are local observations, not a hardware guarantee. An early browser test accumulated playback underruns; a short test in the final Chrome tab showed zero.

Because the browser and a benchmark client cannot both control the same stream, benchmark-demo.py used a second server on port 8081. The browser’s own “playback underruns” counter measures buffering from the viewer’s perspective; the script separately counted received frames, server ticks and planning acknowledgement.

What the tests do not prove: sustained 50 Hz stream delivery under long use, consistent low input latency, GPU performance, physical tracking quality, Unreal integration, or retargeting to Manny/MetaHuman. Project 1 proves the local G1 inference and learning interface work.

8. Known boundaries and next scientific question

Installed now

Kinematic G1

CPU inference, 15 styles, target-pose inspection, local WebSocket streaming, a bone viewer, keyboard/pad movement, and a bounded hop. Live SONIC/MuJoCo controls are visibly disabled because this build did not enable physics. No Kimodo clip is preloaded.

Not established

Real-time character system

There is no direct Unreal connection in this project, no skinned avatar, and no GPU measurement. A future project should separate planner latency, stream rate, browser buffering and retargeting cost before claiming live-game suitability.

The strongest next experiment is to hold the same movement/style sequence constant while measuring CPU plan time, WebSocket acknowledgement time, server tick rate and viewer underruns. That causal decomposition tells us whether the bottleneck is inference, scheduling, stream delivery or browser playback. The field guide’s experiments begin with that mindset.
